# これから作りたい機能と、先に決めること

v0.1.16で**専用サーバーへ参加し、同じ惑星のプレイヤーを見るマルチプレイの基礎**を追加しました。UserNameの初期設定、名前とは別の10桁UserID、プロフィール写真、位置・向き・歩行・服・装備オーラの同期があります。**実績と常時Luckのお宝は、まだ実装していません。** この文書は、次に何を決めて何を作るかを整理するメモです。

## 1. マルチプレイの次の段階

今の通信は、WinHTTPの専用ワーカーが約10回/秒で専用サーバーと更新します。最大32人で、相手は同じ惑星だけをブロックアバターとして表示します。近い4人は詳細オーラの対象にし、他の人のエフェクトは少数の星などで軽くします。VRMは送受信しません。サーバー用Python、Linuxのsystemd設定、HTTPSのCaddy設定は同梱していますが、**XServer VPSへの配備はまだ行っていません。** [PC内で試す方法とVPSの手順](multiplayer.md)を先に使えます。

抽選・所持品・Luck・ロール回数は、引き続き各自のPCに保存します。次に公平な進行やランキングを共有するなら、**誰のデータを、誰が正しいと判断するか**をサーバー側へ移す必要があります。

| 次に用意するもの | 今の状態と次の案 | 必要になる理由 |
| --- | --- | --- |
| VPSの運用 | XServer VPSへPythonサーバーを配備し、CaddyでHTTPSを受ける | PC内テストから、友達が接続できる常時稼働先へ進む |
| プレイヤーIDの引き継ぎと復旧 | 現在は10桁ID＋Windowsが保護する秘密鍵（DPAPI）。次はアカウント認証・復旧方法を決める | 名前を変えずに識別できても、別PCへの移行や紛失時の復旧は別の仕組みが必要 |
| サーバー主体の抽選・所持 | ロール要求をサーバーが検証・抽選・保存する | F1で変更できるローカルデータを、公平な共有進行の根拠にしないため |
| データベースとバックアップ | 所持数、実績、お宝の取得記録を安定したIDで保存する | 更新や障害があっても、二重付与や記録消失を防ぐ |
| 管理と認証の機能 | 招待、権限、BAN、通報、接続・不正対策の記録を設計する | 友人との小規模な部屋から公開コミュニティへ広げるため |
| 部屋と人数の拡張 | 現在は1サーバー最大32人。将来、部屋分けや惑星ごとの配信範囲を検討する | 人数を増やしたときの通信量と描画量を抑える |

たとえばロール時にクライアントが「Singularityが出ました」と送る方式では、入手をサーバーで保証できません。次の構成では、サーバーが「ロールしたい」という要求を受け、クールタイム・惑星・有効なLuckを確認し、結果と所持数を保存してから返します。通信を送り直しても二重にロールしないよう、要求ごとのIDも用意します。F1の試作表示は、現在と同じく所持品を増やさない確認操作として残せます。

コードの出発点は`src/core/aura.cpp`の抽選と所持品です。DirectXを使わない計算を`src/core`に保つと、抽選ルールを画面とは別に検証できます。将来Pythonサーバーへ抽選を移す場合は、同じ確率と惑星制限になるテストも必要です。位置表示では、現在すでに「通信ワーカーがSnapshotを更新 → 描画が一覧を読む」という分け方を使っています。

今の姿の同期は、位置・向き・移動状態・オーラIDなどを送り、粒子一つ一つは各PCで描きます。相手の位置の補間、通信が止まった相手の退出、再接続の処理も土台に含みます。これからは実際のVPSで、遠い回線・混雑時・サーバー再起動時の動作を確認します。

サーバー主体の進行を公開する前に、バックアップ、障害時の復旧、サーバー費用、更新手順を用意します。デバッグ用の所持品・Luck変更と、公開サーバーの正規進行は権限を分ける方針です。

## 2. 実績

最初は「100回ロール」「初めて砂漠へ到着」「Singularityを初めて入手」など、ゲームの操作から判定できる少数の実績が作りやすいです。

| 用意するもの | 例 | 注意すること |
| --- | --- | --- |
| 変わらない実績ID | `roll_100` / `visit_desert` | 表示名や説明を変えても同じ実績として保存する |
| 判定に使う出来事 | ロール確定、惑星到着、初入手 | F1プレビューを入手として数えない |
| 進行と達成の保存 | 現在値、達成済み、達成時刻 | 起動し直しても失わず、条件を満たしても二重付与しない |
| 一覧と通知 | 未達成条件、進捗、達成通知 | 日本語・英語の両方を用意する |
| 報酬を付けるなら付与記録 | 称号やLuckなど | 表示だけの達成と報酬の付与を分ける |

実装の流れは「ゲームで出来事が発生 → 実績の判定 → 達成データを保存 → 通知」です。判定を画面のボタンやアニメーションに埋め込まず、ロール確定などの処理から呼び出すと整理しやすくなります。

現在のロール回数はF1で自由に変更できます。将来の実績では、表示用カウンターを条件にするか、デバッグ変更を含めない実際の記録を別に持つか決めます。マルチプレイヤーで公平性を保証する実績は、サーバー側の記録で判定します。

セーブ形式へ実績を追加するときは、古いセーブを読んだ場合の初期値と移行処理も必要です。追加・名前変更・削除を想定し、配列の何番目かではなくIDで保存する方針にします。

## 3. 惑星ごとのお宝と、常時Luck

お宝は「ステージ上の場所」と「一度取得した事実」を分けて管理します。惑星に入り直すたびに生成されても、同じお宝から何度もLuckを得ないようにします。

| 用意するもの | 例 | 必要になる処理 |
| --- | --- | --- |
| お宝の固定ID | `desert_treasure_01` | 所持済みの判定と保存 |
| 出現する惑星と位置 | 砂漠のX/Z座標 | その惑星だけに配置し、到達可能か確認 |
| 取得方法 | 近づいてキーを押す | 距離・入力・取得済みを確認 |
| 効果の定義 | 常時Luckを加算／乗算 | 数値の上限と合成順を決める |
| 見た目と一覧 | 未取得は光る、取得後は印が付く | 再起動・惑星移動後も同じ状態を表示 |

Luckの計算は、一つの場所にまとめます。たとえば「基礎Luck＋お宝の加算分」を求め、その後に装備やポーションの倍率をかける案があります。ただし、**足し算と掛け算の順番、上限、将来の一時効果との重なり方は、実装前に決める仕様**です。

現在の `Roller::setLuck()` は、抽選表の累積確率（CDF）を変換してレア側へ寄せる方式です。「Luckが2なら全オーラの確率が単純に2倍」という意味ではありません。新しいLuck計算で得た最終値をここへ渡し、現在の惑星で対象外のオーラが出ないことも確認します。

保存するのは、計算済みのLuckだけでなく「取得したお宝IDの一覧」です。起動時に定義から効果を足し直すと、お宝の効果量を調整しても整合性を保ちやすくなります。マルチプレイヤーでは、取得できる距離や重複をサーバーでも確認します。

## 小さく進める順番

1. 基礎接続済みのマルチプレイを、PC内の2人で確認する。
2. XServer VPSへ配備し、回線越しの参加・退出・惑星移動・サーバー再起動を確認する。
3. 公平な進行を共有する場合、アカウント認証・復旧・管理を決め、抽選と保存の権限をサーバーへ移す。
4. 実績・お宝へ着手するときに、固定IDと古いセーブの移行、ロール確定・惑星到着の出来事の受け取り方をそろえる。
5. 実績1個・お宝1個から始め、再起動や再接続でも重複付与されないことを確かめる。

この順番は提案です。今回追加したのはマルチプレイの基礎接続と表示で、実績・お宝・それらの報酬はまだ追加していません。
