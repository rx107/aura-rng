# これから作りたい機能と、先に決めること

この文書は今後の設計メモです。**マルチプレイヤー・実績・常時Luckのお宝は、まだゲームへ実装していません。**
最初から全部を作るより、下の順に一つずつ土台をそろえると、途中で作り直す量を減らせます。

## 1. マルチプレイヤー

今のゲームは、自分のPCで抽選・保存・描画を行います。友達の姿を同じ場所へ表示するには、PC同士をつなぐだけでなく、**誰のデータを、誰が正しいと判断するか**も決める必要があります。

| 先に決めること | 最初の案 | 必要になる理由 |
| --- | --- | --- |
| 一緒に遊ぶ単位 | まず少人数の部屋で同じ惑星を歩く | 大人数・取引・ランキングまで一度に作ると管理範囲が広がる |
| 部屋を動かす場所 | 友達のPCをホストにするか、専用サーバーを置くか選ぶ | ホスト方式は退出時の扱い、専用サーバーは継続費用・更新・監視が必要 |
| プレイヤーの識別 | 表示名と別に、変わらないユーザーIDを用意する | usernameは自由に変更できるため、所持品の持ち主を名前だけで区別できない |
| ログイン方法 | 利用するアカウント基盤を選ぶ | 別PCへの引き継ぎ、なりすまし対策、アカウント復旧の方法が変わる |
| 抽選・所持品の管理 | 公平な進行を共有するならサーバーで確定する | クライアントのLuck・ロール回数・セーブは、開発用に変更できる |
| 通信の方法 | 部屋への参加、位置送信、切断を扱う通信ライブラリー／方式を選ぶ | 遅延、再接続、バージョン違いへの対応が必要 |

「他の人のキャラを見たい」だけの協力用の部屋と、「公平なレア獲得を保証したい」ゲームでは、必要な仕組みが違います。まずどちらを目標にするか決めます。後者なら、ロール要求を受けたサーバーがクールタイム・惑星・有効なLuckを確認し、結果と所持数を保存してからプレイヤーへ返す構成が適しています。通信を送り直しても二重にロールしないよう、要求ごとのIDも必要です。

コードの出発点は `src/core/aura.cpp` の抽選と所持品です。DirectXを使わない計算を `src/core` に保ち、画面を描く `src/render` とは分けておくと、同じルールをサーバーへ持っていきやすくなります。通信の受信処理から直接描画せず、「現在のプレイヤー一覧」を更新して、描画はその一覧を読む形にします。

姿の同期では、位置・向き・移動状態・表示オーラのIDを送り、粒子一つ一つは各PCで描けば通信量を抑えられます。遅れて届いた位置を滑らかにつなぐ補間、退出した人の消去、再接続時の状態復元も必要です。VRMは再配布許可のあるモデルを使うか、モデルを送らず標準アバターで表示する扱いを決めます。

公開前には、データベースのバックアップ、障害時の復旧、サーバー費用、更新手順を用意します。デバッグ用の所持品・Luck変更と公開サーバーの正規進行は、権限を分ける必要があります。

## 2. 実績

最初は「100回ロール」「初めて砂漠へ到着」「Singularityを初めて入手」など、ゲームの操作から判定できる少数の実績が作りやすいです。

| 用意するもの | 例 | 注意すること |
| --- | --- | --- |
| 変わらない実績ID | `roll_100` / `visit_desert` | 表示名や説明を変えても同じ実績として保存する |
| 判定に使う出来事 | ロール確定、惑星到着、初入手 | F1プレビューを入手として数えない |
| 進行と達成の保存 | 現在値、達成済み、達成時刻 | 起動し直しても失わず、条件を満たしても二重付与しない |
| 一覧と通知 | 未達成条件、進捗、達成通知 | 日本語・英語の両方を用意する |
| 報酬を付けるなら付与記録 | 称号やLuckなど | 表示だけの達成と報酬の付与を分ける |

実装の流れは「ゲームで出来事が発生 → 実績の判定 → 達成データを保存 → 通知」です。判定を画面のボタンやアニメーションに埋め込まず、ロール確定などの処理から呼び出すと整理しやすくなります。

現在のロール回数はF1で自由に変更できます。将来の実績では、表示用カウンターを条件にするか、デバッグ変更を含めない実際の記録を別に持つか決めます。マルチプレイヤーで公平性を保証する実績は、サーバー側の記録で判定します。

セーブ形式へ実績を追加するときは、古いセーブを読んだ場合の初期値と移行処理も必要です。追加・名前変更・削除を想定し、配列の何番目かではなくIDで保存する方針にします。

## 3. 惑星ごとのお宝と、常時Luck

お宝は「ステージ上の場所」と「一度取得した事実」を分けて管理します。惑星に入り直すたびに生成されても、同じお宝から何度もLuckを得ないようにします。

| 用意するもの | 例 | 必要になる処理 |
| --- | --- | --- |
| お宝の固定ID | `desert_treasure_01` | 所持済みの判定と保存 |
| 出現する惑星と位置 | 砂漠のX/Z座標 | その惑星だけに配置し、到達可能か確認 |
| 取得方法 | 近づいてキーを押す | 距離・入力・取得済みを確認 |
| 効果の定義 | 常時Luckを加算／乗算 | 数値の上限と合成順を決める |
| 見た目と一覧 | 未取得は光る、取得後は印が付く | 再起動・惑星移動後も同じ状態を表示 |

Luckの計算は、一つの場所にまとめます。たとえば「基礎Luck＋お宝の加算分」を求め、その後に装備やポーションの倍率をかける案があります。ただし、**足し算と掛け算の順番、上限、将来の一時効果との重なり方は、実装前に決める仕様**です。

現在の `Roller::setLuck()` は、抽選表の累積確率（CDF）を変換してレア側へ寄せる方式です。「Luckが2なら全オーラの確率が単純に2倍」という意味ではありません。新しいLuck計算で得た最終値をここへ渡し、現在の惑星で対象外のオーラが出ないことも確認します。

保存するのは、計算済みのLuckだけでなく「取得したお宝IDの一覧」です。起動時に定義から効果を足し直すと、お宝の効果量を調整しても整合性を保ちやすくなります。マルチプレイヤーでは、取得できる距離や重複をサーバーでも確認します。

## 小さく進める順番

1. オーラ・お宝・実績の固定IDと、古いセーブの移行方針をそろえる。
2. ロール確定・惑星到着などの出来事を、画面と独立して受け取れる形にする。
3. オフラインで実績1個、お宝1個を作り、再起動しても重複付与されないことを確かめる。
4. マルチプレイヤーは人数・部屋・アカウント・サーバーの方針を決め、まず2人の移動表示から試す。
5. 公平な進行を共有する場合、抽選と保存の権限をサーバーへ移す。

この順番も提案です。今回は準備事項の文書化までで、ゲーム内の機能や報酬は追加していません。
